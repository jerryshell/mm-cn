## 一、游戏的本地化是怎么工作的

### 数据在哪

14 张 CSV 表存在 `MM_Data/resources.assets` 里，是普通的 Unity `TextAsset`：

```
Data/Localisation/Dilemmas       Data/Localisation/Frontend
Data/Localisation/MediaReports   Data/Localisation/Interviews
Data/Localisation/Tweets         Data/Localisation/Messages
Data/Localisation/PreRaceTalk    Data/Localisation/RaceEvent
Data/Localisation/Shared         Data/Localisation/Simulation
Data/Localisation/TeamRadio      Data/Localisation/Tutorials
Data/Localisation/Nationalities  Data/Localisation/Challenges
```

表头长这样，每种语言一列：

```csv
"Game Area","Source","Criteria","Who","English","ID","Trigger","User Data",...,"French","Italian",..."Russian"
"Navigation","Bottom Bar","","HUDText","Drivers","PSG_10000002","","",...,"Pilotes","Piloti",..."Пилоты"
```

游戏启动时 `LocalisationReader.LoadFromFile()` 用 CsvHelper 读表，按 `ID` 列建索引，
每行的每种语言各存一份文本。

### 语言是怎么选的

这是最关键的一点：**游戏的语言不是用户在设置里选的**。

```csharp
// Localisation.Start()
if (SteamManager.Initialized)
    currentLanguage = SteamApps.GetCurrentGameLanguage();   // ← 跟 Steam 客户端语言
else
    currentLanguage = Application.systemLanguage.ToString();

// GamePreferences.SetLanguage(...)                            ← 设置界面调用的这个方法
{                                                              //   是空的
}
```

`PreferencesManager.HandleSteamLanguage()` 也只在 Steam 语言变化时同步一次。
设置界面里的语言下拉框能选、能存，但不会真的切换语言。

`ConvertStringToLanguage()` 只认这几个名字：

```
English  French  Italian  German  Spanish  Brasilian  Dutch  Hungarian  Polish  Russian
```

现代 Steam 客户端返回的是 `schinese` / `tchinese` / `koreana` 这类字符串，
一个都匹配不上，`currentLanguage` 会**保持默认的 English**。

**结论**：只在某一列写中文，等于大部分玩家看到的还是英文。
补丁因此把全部 10 个语言列都覆盖成中文，这样无论 Steam 语言是什么都能显示中文。

### 顺带解决的日期/数字格式

`UpdateNumberFormattingEnums()` 按语言名决定小数点和日期序数：

```csharp
if (mCurrentLanguage == "English") { 小数点 "."; 千分位 ","; }
else                               { 小数点 ","; 千分位 " "; }
```

中文列如果单独新增一种语言，还得改 `supportedLanguages` 和这段逻辑（都要动 DLL）。
沿用英文格式反而最省事：计时、圈速、百分比都还是 `1:23.456` 和 `30%`，符合国内观赛习惯。

## 二、翻译引擎的行为与对策

用的是腾讯 Transmart 的网页接口（`transmart.qq.com/api/imt`，固定 client_key，不需要注册）。
实测下来它在处理「带标记的游戏文本」时有一堆脾气。

### 占位符会被吃掉

原文里的三种标记必须原样保留：

```
<gender^Subject=F>她…</gender>        性别分支（英文里是 she/he，中文里是 她/他）
<font="CooperHewitt-Bold">…</font>    富文本
{Player:FirstName}                    对白变量
```

各种占位符形式的实测结果：

| 占位符 | 结果 |
| --- | --- |
| `[[V0]]` | **会被删掉**，或者被改写成 `[2019-01-15 00:00:00]` 这种日期 |
| `［［V0］］` | 同上 |
| `【0】` | 被规范化成 `[0]` |
| `{0}` | 所有位置都稳定保留 ✅ |
| `{v0}` `{_0_}` | 也稳定，但没必要 |

于是统一用 `{n}`（见 `tools/markup.py`）。

### 数字/货币格式会吃掉左花括号

`{n}` 也不是万能的 —— 紧跟在数字或符号后面时，引擎会把它当成格式说明符：

| 输入 | 引擎返回 |
| --- | --- |
| `Reliability: +30%{2}` | `可靠性：+30% 2}` ← 左花括号没了 |
| `Reliability: +30${1}` | `可靠性：+30$100}` |
| `Reliability: +300{1}` | `可靠性：+300 0}` |
| `Reliability: +30.{1}` | `可靠性：+30. 00}` |

对策：`protect()` 里会把紧贴占位符的**无字母串**（`+30%`、`$`、`300` 这类）
一起并进占位符，让引擎看到的是 `+30{2}` 而不是 `%{`：

```
原文:      <font…>Reliability:</font> +30%<font…>Red Zone:</font> +35%
保护后:    {0}Reliability:{1} {2}Red Zone:{3} +35%
           tokens[2] = "+30%\n<font=CooperHewitt-Bold>"
```

判断依据是「这段紧贴的字符里有没有字母」：`+30%` 没有字母 ⇒ 并进去；
`do.{2}`（句号后接换行）里有字母 ⇒ 不动，因为它本来就是正常的标点+换行。

### 占位符太多会直接拒翻

引擎对「占位符密度过高」的输入会**原样回显**不翻译。这类结果占位符是完整的，
只查占位符查不出来，必须额外判断「返回是否等于输入」。

对策是两个：

1. 连续标记合并成一个占位符 —— `</gender>\n<gender^X=M>\n` 变成一个 token
   而不是四个，占位符密度显著下降；
2. `_refused()` 专门识别「原样回显」，命中就降级重译。

### 三轮降级

`translate_many()` 按下面的顺序处理，每一轮只处理上一轮失败的：

| 轮次 | 粒度 | 说明 |
| --- | --- | --- |
| 1 | 整句 | 一次送到位，实测 **98.6%** 在这里就过了（11501/11605） |
| 2 | 按行 | 按含换行的占位符切单元，分别翻 |
| 3 | 按片段 | 把单元再切成占位符之间的纯文本片段逐个翻，短标签在这轮命中 |

三轮都过不去才写进 `trans/zh_failed.jsonl`。最终结果是 **0 条失败**。

### 还会残留英文词首

句子紧跟在 `<gender…>` 标记后面时，引擎有时会把第一个英文词留下：

```
{0} I like what I see with …   →   {0}I我喜欢我看到的…
```

`glossary.FIXES` 里有一条正则专门收拾这种情况：行首的 `I / It / Of / We / My / If`
这类功能词，如果后面**直接**跟着汉字就删掉。写成区分大小写是为了不误伤
`IT部门`、`iPhone手机` 这种。

## 三、字体

### 为什么必须重做

游戏 UI 用的是 TextMesh Pro 的**位图 SDF 字体**：字形不是矢量，而是预先渲染进
一张 `Alpha8` 图集的「有符号距离场」。UI 文字（4774 个 `TextMeshProUGUI` 组件）
指向 11 个字体资产：

| 字体 | PointSize | 用它的组件数 |
| --- | ---: | ---: |
| CooperHewitt-Medium SDF | 52 | 2625 |
| CooperHewitt-Bold | 50 | 1054 |
| Mission Gothic Regular SDF | 119 | 703 |
| CooperHewitt-Book SDF | 54 | 151 |
| CooperHewitt-Medium SDF（大号副本） | 60 | 108 |
| 其余 6 个 | 51–276 | 1–65 |

图集里只有 88–1004 个拉丁字形，一个汉字都没有。直接塞中文就是一片空白方块。

### SDF 编码

拿游戏自带的图集反推出来的：

```
alpha = 0.5 + distance_px / (2 × _GradientScale)        _GradientScale = padding + 1
```

验证方法：用游戏自带的 TTF（`assets/ttf/`）重新渲染同样的字形，
按这个公式编码，和原图集逐像素比对。`_GradientScale` 在材质里是 6.0，
和字体资产的 `padding=5` 正好对上。

字形表里的 `width` / `height` 是**墨迹包围盒**（不含距离场外扩的那圈），
这一点和 TMP 文档里的说法不一致，是比对出来的。

### 度量必须自洽

TMP 采样图集时，取的是 `[x-pad, x+width+pad] × [y-pad, y+height+pad]` 这块，
再拉伸到 `width × height` 的四边形上。所以只要 `width` 和实际画在图集里的墨迹宽度
差一点点，中文就会被横向拉伸。

`tools/sdf.py` 的做法是：**五个度量全部由同一次 FreeType 光栅化结果推导**，
不另外查 TTF 的轮廓包围盒。校准结果（对着游戏自带的 550 个拉丁字形）：

| 度量 | 平均误差 | p95 | 最大 |
| --- | ---: | ---: | ---: |
| width | 0.102 px | 0.250 | 1.000 |
| height | 0.118 px | 0.250 | 0.438 |
| xOffset | 0.087 px | 0.188 | 0.375 |
| yOffset | 0.141 px | 0.312 | 0.375 |
| xAdvance | 0.123 px | 0.312 | 0.375 |

另一处需要注意的地方：`yOffset` 是「基线到墨迹**顶部**」的距离，不是到墨迹底部。
一开始写成了底部，结果中文整体下沉了一个字高。

### 图集的排布与显存占用

原图集内容**像素级保留**在画布左上角，中文字形用货架装箱算法排在右侧和下方。
4096×4096 的 Alpha8 图集 = 16 MiB，11 个字体共约 180 MiB 显存。
几个超大字号（PointSize 119 / 270 / 276）的标题字体做了等比缩比，
缩比后 PointSize 同步变小，显示尺寸不变、源分辨率降低，省下约 50 MiB。

### 距离场缩放

把浮点距离场从一个大尺寸缩到另一个尺寸时，**必须用 `Image.F` 模式**
（32 位浮点）做缩放：

```python
# 正确
Image.fromarray(cell.astype(np.float32), 'F').resize((tw, th), Image.BOX)

# 错误：'L' 模式会把 -17..+3 的距离值当成 0..255 的亮度裁剪，
#       字形会糊成一片斑点
Image.fromarray(cell, 'L').resize((tw, th), Image.BOX)
```

这个 bug 的症状很容易误判成「SDF 算法错了」，因为图集里看到的是一团马赛克。

## 四、校验

分三层，都能在不启动游戏的情况下跑：

| 脚本 | 检查对象 | 内容 |
| --- | --- | --- |
| `tools/verify.py` | 构建产物 `dist/` | 表结构、语言列一致性、`{n}` 泄漏、图集与字形 |
| `tools/accept.py` | **已安装到游戏的文件** | 同上 42 项，发布前的最后一道关 |
| `tools/preview.py` | 字形数据 | 按 TMP 排版算法渲染成图片 |

`preview.py` 是三层里最有说服力的：它复刻了 `TMP_Text` 的四边形摆放、UV 计算和
距离场解码，所以图上看到的就是游戏里画出来的样子 —— 中英文混排的基线、
字距、字重都能一眼确认。

## 五、其他实现细节

### 装过补丁之后不能再拿游戏目录当输入

`resources.assets` 打上补丁后约 373 MiB（原版 214 MiB）。如果之后再跑
`extract.py` / `build_patch.py` 而它们去读游戏目录，就会：

* 把中文当成「英文原文」导出，翻译缓存全部失配；
* 把已经缩比过的图集**再缩一次**（PointSize 从 119 变成 17），产出的字体是废的。

对策是 `mmcore.pristine_assets()`：优先用安装脚本留下的 `resources.assets.orig`，
两个文件都是汉化版时直接报错退出。任何读游戏资源的脚本都应该走这个函数。

### `.bat` 必须用 GBK 存

cmd.exe 按系统 ANSI 代码页解析批处理文件。UTF-8 的中文在 936 代码页下会被拆成
一堆乱码字节，脚本会以「不是内部或外部命令」的形式崩掉。
所以 `installer/*.bat` 由 `scripts/make_installer.py` 生成，编码固定为 GBK，
且 `.gitattributes` 里声明了 `*.bat -text`，避免 git 做换行归一化。

批处理里所有**语法**保持 ASCII，中文只出现在 `echo` / `rem` 里 ——
这样即使用户的代码页不是 936，最多是提示文字乱码，安装逻辑仍然正确。

### 语言列全写中文的副作用

设置界面的语言下拉框会列出「英语 / 法语 / … / 简体中文」，但选哪个都是中文。
`glossary.ID_MAP` 把语言名也翻成了中文（对应 PSG_10010782 到 PSG_10010791）。
